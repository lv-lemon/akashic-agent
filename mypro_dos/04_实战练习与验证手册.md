# 实战练习与验证手册

原则：一次实验只验证一个机制；使用独立 HOME/state/workspace/plugin home/config，保存自己的操作和结果。本文提供实验设计，本次整理未执行服务或测试。

## 1. 准备可重复的环境

先看 [产品启动](../docs/design/product-startup.md)。Windows 初学者优先用 Docker Desktop；源码入口 `./start` 适用于 Linux/WSL2。当前 [mise.toml](../mise.toml) 固定了开发工具版本，而 pyproject 的最低 Python 版本只是包元信息；当前代码出现 PEP 695 类型语法，不应仅凭 README 的最低版本就断言所有开发路径兼容。

在 PowerShell 先做只读检查：

```powershell
git -c core.fsmonitor=false rev-parse HEAD
git -c core.fsmonitor=false status --short
python --version
node --version
docker compose version
```

运行学习实例时选择新的 state 目录和独立 Compose project/数据卷。产品默认目录可能与已有实例重叠，先核对实际路径。仓库 Compose 从明确的源码提交构建；未提交修改不会自动成为镜像里的代码。README 的 release 下载流程则可能与当前 checkout 不同，追踪源码时要记录运行 revision。

源码开发需要正式构建并安装所选插件发行制品，不能只 `main.py init` 后假设源码插件全部自动加载。构建、安装参数先查看脚本，不向日常实例试装：

```powershell
python scripts/build_plugin_distribution.py --help
python scripts/install_plugin_distribution.py --help
```

环境不足时先读现有场景源码，记录“未运行”和阻塞原因。不要为完成学习清单而覆盖现有配置或清空数据。

## 2. 实验 A：观察完整对话与工具回合（必做）

**问题：** 一次模型输出的工具调用何时成为事实，何时执行？

阅读 [bundle_modes_scenario.py](../scripts/bundle_modes_scenario.py) 的 `headless_reply`，了解隔离 HTTP 模型如何经过真实 driver、Models、Reply、Ledger 和 Gateway。这个场景的固定回复证明本地链路，不证明远程模型推理能力。

在自己的隔离实例里，发一个只产生临时文件的受控任务，例如在学习用目录写入固定文本后读取。记录 Input、含 ToolCall 的 Output、ToolResult、最终 Output 的身份与顺序，并关联工具进程与真实文件。

验收：能把模型工具请求、持久 Output、实际执行、结果消息四个时刻分开；重开会话后读取已保存事实。保留源码入口、日志片段和文件内容，避免只截一张聊天截图。

## 3. 实验 B：新输入、暂停与旧草稿（必做）

**问题：** 如果模型还在生成，用户又发了新消息或暂停，旧回复是否还可以提交并执行工具？

阅读 `react` 的 `commit/narrow/_competing`，以及 conversation/sources 的输入与控制入口。在隔离模型端设置可控等待：旧请求开始后追加新输入或暂停，再释放旧响应。

预期观察：旧生成可能产生预览或费用，但失效草稿不能越过提交前提触发工具。分别记录新消息/控制提交、旧生成返回、Output 是否提交和外部标记是否产生。不要把仅客户端隐藏旧气泡当成验证。

## 4. 实验 C：并行执行但结果按序提交（进阶必做）

**设计：** 用隔离场景工具 A、B、C。A 等待约 1 秒，B 等待约 0.1 秒，均声明允许并行；C 声明非并行。固定模型调用次序为 A、B、C。

观测 A/B 开始与完成时间、两条结果的提交次序、C 的启动时刻。预期 A/B 重叠，B 可以先完成，但结果按 A、B 提交；C 等前组结算。再注入 A 在结果提交前失败的情况，查看后继提交门行为。

参考：[test_parallel_tool_calls.py](../tests/test_parallel_tool_calls.py)、`react:_settle_pending/_OrderGate`。既有测试用于阅读与按需运行；项目 [WORKFLOW](../docs/WORKFLOW.md) 禁止新增单元测试，自己的实践应做真实组件集成或隔离场景，避免新增函数 mock 测试。

## 5. 实验 D：工具执行中崩溃（高价值）

在一次性目录中让受控工具先追加一个唯一标记，再等待。观察 ToolCall Output 已提交、工具已经开始后，终止该隔离 gateway 进程；只操作自己创建并记录的 PID。重新启动同一隔离 state，读取对应消息。

当前默认消息调用的预期：副作用标记不因恢复被自动再次追加；未结旧调用得到 error“结果未知”，模型再根据当前材料决定后续动作。不要在真实发送、支付或删除工具上做这个实验。

依据：`tools/execution.py:_settle_message`、[ADR-0100](../docs/decisions/0100-message-tool-calls-recover-at-turn-granularity.md)。现有 [ledger_runtime_scenario.py](../scripts/ledger_runtime_scenario.py) 关注真实 Ledger/Channel 的崩溃与换代，可辅助理解；它不自动覆盖你的全部工具副作用场景。

补充对照：在结果已提交后重启，应该复用结果事实。进程崩溃实验不能证明断电耐久性。

## 6. 实验 E：压缩后的历史完整性（必做）

在隔离实例创建足够长的会话，使用本地支持的配置或场景路径触发摘要，记录摘要引用区间和模型实际请求。压缩前后比较原消息正文、身份、顺序；重开会话读取完整历史。

验收同时满足：模型请求变短或改用摘要；原历史仍可读；工具对不被切断。消息总行数不变不足以证明正文没有被改写。

入口：[context/plugin.py](../plugins/context/plugin.py)、[compaction](../plugins/compaction/)、[test_context_history_contract.py](../tests/test_context_history_contract.py)。需要真实摘要模型时记录模型与费用，使用固定响应的本地组件场景只能验证结构协议。

## 7. 实验 F：插件撤回与资源生命周期（选做）

选一个学习实例中的简单插件，从正式更新/启停路径触发变化。记录提供的服务、注入的消费者、端点、活动调用和清理完成时刻。验证撤回后新调用行为、旧活动工作如何结束，以及退出后是否留下任务或连接。

参考：[test_plugin_composition_lifecycle.py](../tests/test_plugin_composition_lifecycle.py)、[builtin_disable_matrix_scenario.py](../scripts/builtin_disable_matrix_scenario.py)、[agent/plugin_composition/context.py](../agent/plugin_composition/context.py)。避免直接修改安装 cache 来模拟源码开发；不要假设换 live 指针可以回滚外部操作。

## 8. 把一次练习做成可讲的真实改动

| 方向 | 建议范围 | 证据与边界 |
|---|---|---|
| 日志可观测性 | 在确有缺口的链路增加阶段或身份关联 | 先证明缺口；日志不写凭据和消息正文；比较同条件 trace |
| 错误诊断 | 改善一个已复现错误的可操作提示 | 展示触发、错误分类与新提示；不把未知改成成功 |
| 普通插件 | 一个只操作学习临时目录的简单工具 | 走正式插件合同、授权与生命周期；演示禁用后行为 |
| 隔离恢复场景 | 用真实组件补一个此前缺少的故障边界 | 比较真实状态与副作用，不用场景名包装单元 mock |

选择时先确认问题真实存在。不要为了简历强行引入 Redis、消息队列或分布式多 Agent；基础项目未证明需要这些组件。

开发前写四句话：现状是什么、要改什么、状态 owner 是谁、怎样看到正确结果。非简单代码修改按仓库要求使用独立 worktree；当前学习笔记本身无需构建环境。

## 9. 性能评估怎样做才可信

按 [ReAct 测量说明](../scripts/react-performance/README.md) 开启适用的 timing，先核对当前打点，再采集自己的 trace。`AKASHIC_TIMING=1` 与 `AKASHIC_LOG_FORMAT=json` 是说明中的采集开关。

固定源码提交、模型、上游、输入、输出预算、工具权限与上下文规模；区分冷启动和热态，保留失败与超时样本。至少记录输入到首请求、首个有效 delta、各轮间隔、工具 batch 时间、提交时间与最终任务完成证据。

若做优化，报告同条件前后分布、样本数量和未归因时间。样本少就称观察，不声称稳定的 P95 提升。仓库历史 benchmark 数字也不是自己的实验成绩。

```markdown

要验证的机制与预期：
执行命令、输入及故障注入时机：
实际消息身份、日志关联 ID、文件或数据库观察：
结果与预期是否一致：
未验证层次、异常与可能干扰：
清理了哪些本次临时资源：
60 秒面试讲解：
```

完成 A、B、D、E，再带一个自己的小改动，通常比通读所有插件但没有证据更能支持深入追问。C 则是解释异步并发与一致性最值得准备的一项。
