# 面试问答与项目表达

以下回答是练习骨架。每题先用自己的话回答，再打开源码补齐细节；不要把未运行的场景说成亲测结果。

## 1. 两分钟项目介绍

> 我深入学习并实践了 Akashic Agent，一个支持持续对话、工具执行、记忆与主动消息的个人 Agent 项目。我的重点是从输入接纳、回复调度、ReAct 循环到工具结果落盘的完整链路。
>
> 它把业务做成普通插件：Ledger 拥有消息事实与事务，Models 管理模型连接和生成，Context 组装模型请求，Tools 管理执行与授权，Core 提供组合和生命周期。这样可以把能力扩展和资源管理分开讨论。
>
> 我主要研究了三个问题：生成期间新输入到达后如何阻止旧草稿提交；并行工具如何重叠执行又按模型顺序提交结果；进程崩溃后如何用日志恢复并诚实表达未知外部效果。接下来我会用自己实际完成的实验或改动说明其中一个机制。

最后一句替换为自己的事实：具体改了哪里、怎样复现、看到什么结果。尚未动手时使用“源码学习与机制分析”，不要使用“负责系统设计”“支撑生产规模”。

## 2. 主链与架构问题

### Q1：一次用户输入怎样变成回复？

先讲逻辑链：Channel/客户端输入 → conversation/sources 接纳并提交 Input → reply 监听与调度 → reply_program 绑定资源 → react 取得材料并调用模型 → 提交 Output → 若含工具则结算并继续。外部送达另由相应插件负责。

证据：[conversation/plugin.py](../plugins/conversation/plugin.py)、[reply/plugin.py](../plugins/reply/plugin.py)、[reply_program/program.py](../plugins/reply_program/program.py)、[react/plugin.py](../plugins/react/plugin.py)。追问时说明这包含事件通知与调度，不是一条同步函数调用栈。

### Q2：为什么不只写 while 循环调用 LLM？

循环本身很短，困难在循环之外：输入与工具结果身份、并发输入、权限、资源清理、生成失败、外部效果不确定以及重启后继续。用“工具执行了但进程没来得及记录结果”说明持久事实和恢复协议的必要性。

### Q3：为什么消息采用追加事实和投影？是不是 Event Sourcing？

追加事实有助于保留完整历史，由不同投影构造模型窗口、Turn 和界面。可以说具有事件日志与投影思想，但不要直接称为完整 Event Sourcing/CQRS 系统：项目还存在各 owner 的可变状态、模型注册库和外部副作用，需要逐项分析。

证据：[ledger/contract.py](../plugins/ledger/contract.py)、[ledger/log.py](../plugins/ledger/log.py)、[设计原则](../docs/projectneed.md)。

### Q4：插件化的价值和代价是什么？

价值：能力与数据 owner 明确，可通过合同组合与替换，UI、模型、主动任务不必拥有同一生命周期。代价：依赖失效、动态服务撤回、活动调用排空、跨插件合同兼容更复杂。结合 `ctx.inject/effect/runtime_scope` 讲，不能只回答“解耦”。

### Q5：为什么 Core 不直接持有所有数据库？

业务状态由实际 owner 管理，Core 装配宿主与插件。Ledger 发布只读、受限 writer 和 owner 事务等端口，减少消费者获得任意数据库权限的机会。注意多个 Ledger 服务可能共用数据库，一个 owner 不等于一个物理文件。

证据：[bootstrap/tools.py](../bootstrap/tools.py)、[ledger/plugin.py](../plugins/ledger/plugin.py)、[ledger/services.py](../plugins/ledger/services.py)。

## 3. 工具、并发和恢复问题

### Q6：如何防止模型旧草稿执行工具？

模型生成基于固定前缀。提交 Output 时，在事务中检查当前来源控制和竞争消息；同来源新输入、控制或相关结果可能使前提失效。只有成功提交的 ToolCall 才进入后续工具结算。区分界面预览、模型草稿与持久 Output。

证据：`react` 内 `commit/narrow`、`_competing`。追问：如果只在请求模型前检查一次，生成期间 pause/abandon 就可能使旧授权失效。

### Q7：并行工具是否允许先完成先写结果？

当前实现让连续 parallel 调用有界重叠执行，但用 `_OrderGate` 与 `commit_after` 按模型顺序提交 ToolResult。非并行调用形成屏障。不要混淆并发执行顺序和日志提交顺序。

证据：`react:_settle_pending/_settle_group/_run_ordered`、[tools/execution.py](../plugins/tools/execution.py)。历史 ADR 的阶段回执细节需结合 ADR-0100 勘误理解。

### Q8：一个工具调用凭什么有执行权限？

模型只提出调用。程序限定工具视图和固定 binding，执行路径准备并校验参数，再使用授权回调与来源检查。模型自己声明“用户允许”不构成权限。schema 展示与真正授权是两个边界。

证据：[tools/program.py](../plugins/tools/program.py)、[tools/menu.py](../plugins/tools/menu.py)、`ToolExecution._invoke_message`。

### Q9：工具能保证 exactly-once 吗？

不能泛化。唯一结果身份可以防止重复保存某次调用的结果；外部副作用已经发生但结果没落盘时，单靠本地数据库无法知道远端事实。当前默认消息调用重启后将未结旧调用记为“结果未知”，不自动重跑；有业务账本的工具再按自身协议处理。

### Q10：LLM 重试、ReAct 重启和工具重试有什么区别？

同一次模型调用的临时网络重试由 Models 管理请求身份。进程重启后的 ReAct 使用当前材料生成新请求。工具已有结果则复用，旧未结默认调用记录未知。新模型请求不授予重跑工具的权力，费用也可能重复。

证据：[models/state.py](../plugins/models/state.py)、[ADR-0100](../docs/decisions/0100-message-tool-calls-recover-at-turn-granularity.md)。

### Q11：取消 Task 后为什么还要等待清理？

取消是控制信号，外部操作可能已经开始，线程工作也未必能被立即终止。排空保证资源仍被使用时不提前关闭，并收集真实异常；它不能回滚发送、文件写入或已执行命令。结合 ReAct 的 shield/drain 与 RuntimeScope 说明。

### Q12：WAL/NORMAL 能保证什么？

它在性能与故障保证之间作了取舍。项目的 Session/Models 账本采用普通进程崩溃级恢复边界；宿主断电或 OS 崩溃可能丢失最近提交，不能承诺固定时间或事务数量上界。项目 ADR 中的历史回执恢复描述还需以更新的 ADR-0100 为准。

证据：[ADR-0099](../docs/decisions/0099-ledger-commits-use-wal-normal.md)。这是项目选择的说明，不是对所有部署存储介质的实测保证。

### Q13：流式输出已经显示了，是否说明工具和消息已提交？

不能。预览可以早于完整生成和事务提交；输出还可能截断、解码失败或被新输入取代。前端应区分临时预览与持久事实，恢复时以已提交日志为依据。

### Q14：模型返回了合法 JSON 工具参数，但 finish_reason 是 length，可以执行吗？

当前 ReAct 在解码执行前拒绝截断响应。合法 JSON 不能证明生成已经完整，部分工具批次也可能缺失。查 `react` 中的 `OutputLengthError` 分支。

## 4. 上下文、记忆与主动执行问题

### Q15：Context、compaction 和长期记忆分别解决什么？

Context 组装这次模型请求；compaction 用摘要表达已覆盖的历史区间；Markdown profile 保存长期可读材料；Akasha 学习消息并提供图相关召回。原始事实、摘要、profile、向量和图不能互相混用删除策略。

### Q16：上下文超长直接保留最后 N 条可以吗？

作为一般策略要先考虑系统提示、工具 schema、输出预算与工具调用配对。本项目检查已结算边界和摘要覆盖范围。裁切模型视图不能改写原始历史，摘要也不能切开未结算工具对。

证据：`ContextBuilder.build/_summary_cutoff`、`settled_prefixes`、[compaction](../plugins/compaction/)。

### Q17：Akasha 是否就是向量数据库？

不是简单等同。它包含消息消费与学习快照、图结构、特征、扩散与 readout；向量是相关材料的一部分。回答到自己掌握的范围：能追到 consumer 与 recall/readout 后再谈算法，未推导过就不要宣称自己设计了图检索算法。

### Q18：为什么恢复学习图不能随便从头重跑？

必须确认原始消息、绑定、embedding 空间和算法条件。图与消费进度一起推进，缺失材料应明确失败或按既定补算协议处理。重建是显式动作，丢失学习图不等于授权隐式重新学习。

证据：`MessageConsumer.load`、[application/rebuild.py](../plugins/akasha/application/rebuild.py)。

### Q19：主动 Agent 和定时任务有什么不同？

定时只是触发机制。项目还需要候选材料、阶段判断、工具调查、状态推进和送达结算。Wake 使用阶段程序与固定工具范围，Drift 保存提案相关状态，Delivery 管理外部发送。不能由“计划触发了”推出“用户已收到”。

### Q20：插件热更新为什么困难？

旧 provider 可能仍被活动工具、流、端点或数据库访问引用。更新要阻止新调用进入旧实例、等待允许存续的调用排空，并撤回注册和清理资源。Python reload 只能改变一部分代码对象，不能自动解决这些资源责任。

## 5. 评估、排障和取舍问题

### Q21：用户说 Agent 慢，你先看什么？

按输入提交、回复调度、材料取得、请求发送、首个有效 delta、生成结束、Output 提交、工具执行、结果提交、下一轮准备拆分。以关联 ID 对齐日志，不能把整个回合都归因于 LLM。工具并行时间用区间并集或 batch wall time，避免重复累计。

证据：[性能测量说明](../scripts/react-performance/README.md)。代理收到请求只能证明本地边界，不能声称远端已经开始推理。

### Q22：怎样证明 Agent 任务成功？

分开检查协议链路、实际任务产物、受保护状态和资源收束。回复“完成了”、HTTP 200、测试进程退出成功都只是部分证据。修改文件的任务检查真实 diff 与目标行为；恢复任务检查身份、顺序和完整内容。

### Q23：为什么不直接换成某个 Agent 框架？

先说明需求：持续状态、来源控制、普通插件能力、细粒度生命周期与历史兼容。再讨论框架在这些需求上的适配成本。当前源码展示了自有组合与 ReAct 实现；不能据此虚构作者已经评估并否决了所有框架，更不能无基准声称性能领先。

### Q24：项目有什么可以改进的地方？

用当前证据回答一个小问题：例如某条 trace 缺少清晰的阶段归因、某个失败诊断对使用者不够明确，或真实外部资源验收还待补齐。说明现状、影响、最小方案和验证方法。不要把 NOW 中的待复核风险直接说成已确认线上故障。

## 6. 简历与专题准备

可使用的表述模板：

> 基于 Akashic Agent 开展源码分析与二次开发，梳理输入接纳、ReAct、工具执行及消息持久化链路；完成【实际改动】，通过【实际隔离场景】验证【可观察行为】，并分析并发提交、取消与进程恢复边界。

准备两个 8 分钟专题即可：A“并行工具与有序提交”；B“日志事实与崩溃后的未知结果”。每个专题包含问题、调用链、一个时间线或反例、实际证据、代价与限制。

面试前最后自查：是否把源码学习说成原创？是否编了 QPS、成本与提速比例？是否能回答关键函数在哪？是否讲清局部测试不能代替真实模型、设备与生产验收？
