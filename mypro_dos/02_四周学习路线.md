# 四周学习路线

假设每天投入 2～3 小时，目标为 Agent 开发或 Python 后端面试。每天保留三个产出：源码调用点、一个机制的口述、一份观察或待验证问题。阅读多不等于掌握，优先做闭卷复述。

## 1. 基础补齐与时间分配

| 基础 | 最低掌握程度 | 在项目中的对应 |
|---|---|---|
| Python asyncio | Task、取消传播、shield、Event、异步上下文管理器 | 工具排空、提交顺序、退出清理 |
| Python 类型与数据模型 | Protocol、泛型、dataclass、Pydantic | 服务合同、冻结消息、输入校验 |
| 数据库 | 事务、唯一约束、WAL、并发提交 | Ledger、模型调用记录、调用结果去重 |
| LLM API | messages、tool schema、tool call、stream、usage | Models、Context、Tools |
| 服务工程 | readiness、进程生命周期、日志关联、配置隔离 | bootstrap、Supervisor、场景脚本 |

每天建议：20 分钟回顾，60 分钟读一条真实链路，40 分钟调试或场景学习，20 分钟整理并口述。基础薄弱时先增加 3～5 天补齐前两项，不急着推导 Akasha 算法。

## 2. 第一周：把一条对话走通

| 天 | 主题与源码 | 当日产出/验收 |
|---|---|---|
| D1 | README、docs/INDEX、projectneed 设计原则、NOW、目录与依赖 | 一页产品定位，区分当前实现与待验收项 |
| D2 | main.py、bootstrap/app.py、bootstrap/tools.py | 画出启动到 ready 的路径，指出业务数据库在哪里打开 |
| D3 | ledger/contract.py、turn_projection | 写一组含工具调用的消息序列，解释消息身份和 Turn 边界 |
| D4 | conversation、sources、reply | 追踪 Input 提交后谁触发回复；指出 pause/resume 的入口 |
| D5 | reply_program/program.py、react/plugin.py | 不看代码讲每轮循环；定位 Output 提交先于工具执行 |
| D6 | models、tools/program/menu/execution | 追踪一次参数校验、授权、执行、结果提交 |
| D7 | 学习验证手册中的实验 A、B；条件满足后运行隔离实例 | 演示一条回复或解释一份完整场景调用链；说明尚未实测部分 |

第一周结束能回答：输入存哪里？何时允许模型生成？工具调用以什么为事实？最终回复和外部送达为何不同？

## 3. 第二周：掌握 Agent 的工程难点

| 天 | 主题与源码 | 当日产出/验收 |
|---|---|---|
| D8 | context/plugin.py、materials.py | 列出材料获取与请求组装的边界，标注模型预算 |
| D9 | compaction、context 的 settled_prefixes | 用具体消息序列解释为什么不能切断工具对 |
| D10 | markdown_memory、akasha/learning、consumer | 做“原始消息/摘要/profile/学习图/向量”对照表 |
| D11 | Akasha scopes、projects、readout、diffusion | 跟踪一个召回入口；明确哪些算法细节仍不掌握 |
| D12 | react 的 commit、sources 控制、ADR-0025 | 推演生成时新输入到达，说明旧草稿为何不能触发工具 |
| D13 | _settle_pending、_OrderGate、tools/execution | 手画 A/B 并发、C 屏障、按序提交时间线 |
| D14 | ADR-0100、ADR-0099、Models 重试 | 写出“进程崩溃但工具效果未知”的恢复说明 |

第二周结束用 10 分钟讲三个反例：压缩不能删历史、生成重试不能重跑工具、取消不能撤销外部效果。

## 4. 第三周：插件架构与主动执行

| 天 | 主题与源码 | 当日产出/验收 |
|---|---|---|
| D15 | Context、ServiceKey、provide/require/inject | 从一个简单插件列出“提供什么、依赖谁、谁持有状态” |
| D16 | effect、Fiber、RuntimeScope、OwnerCall | 用数据库连接或后台任务解释排空顺序 |
| D17 | PluginManager、watcher、generation、bundle | 区分源码、发行制品、selected 状态与实际 live 状态 |
| D18 | wake/plugin/program/request | 画当前阶段控制，指出阶段工具范围与步数预算 |
| D19 | eventmail、drift、delivery | 分开记录候选、选择、模型输出、发送尝试和送达事实 |
| D20 | jobs、subagent、scheduler 选择一条深挖 | 讲清后台完成通知或子任务回传的真实路径 |
| D21 | 验证手册中的实验 C、D、E，按可用环境选做 | 一个完整演示，附日志与限制，不只附成功截图 |

不要把第三周变成插件目录逐个通读。你的目标是复用同一套分析方法：合同、调用者、owner、生命周期、失败和恢复。

## 5. 第四周：形成自己的面试资产

| 天 | 工作 | 验收 |
|---|---|---|
| D22 | 在验证手册的改动题中选一题，先写现状与目标 | 有真实代码依据和可观察预期 |
| D23 | 实现最小改动，遵循仓库工作流 | 改动围绕一个问题，可解释每处修改 |
| D24 | 验证目标行为、失败行为与相关静态检查 | 保存命令、环境、结果与未验证项 |
| D25 | 阅读 ReAct 性能测量说明，分析自己的 trace | 能区分本地开销与模型等待，不编造提速比例 |
| D26 | 准备 2 分钟项目介绍和 8 分钟专题 | 每个亮点有源码或个人实验支撑 |
| D27 | 模拟面试：问答文档随机抽 10 题并追问 | 录音复盘，只补答不上来的机制 |
| D28 | 闭卷画图、演示改动、整理简历 | 说清学习范围、实际贡献、限制与下一步 |

## 6. 只有七天时

1. D1：产品定位、启动、Ledger 消息模型。
2. D2：Input → reply → reply_program → ReAct 主链。
3. D3：工具授权、并发、结果按序提交。
4. D4：Context、compaction、记忆的职责区别。
5. D5：新输入竞争、取消、模型恢复、未知工具结果。
6. D6：完成一个隔离演示或小改动，整理真实证据。
7. D7：练介绍、架构图和高频追问。

七天路线暂缓图算法推导、Computer 编解码、全部前端组件与全部 ADR。面试时主动说明深挖范围。

```markdown

```

每周按 0～3 分自评：0 不会；1 能解释概念；2 能定位源码；3 有独立演示或行为证据。主链、工具、上下文、恢复至少达到 2 分，再花时间准备更多插件名。
