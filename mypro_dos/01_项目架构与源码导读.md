# 项目架构与源码导读

阅读顺序：先看第 1～4 节串起主链，再看第 5～9 节的工程取舍。本文是基于当前源码的学习地图，不是全部模块的逐行注释。

## 1. 项目全景

```text
┌──────────────────────────────────────────────────────────┐
│ Web / Channel / Python SDK / CLI                         │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│ 业务插件：接纳输入、来源控制、回复、主动唤醒、送达          │
│ conversation / sources / reply / wake / delivery          │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│ reply_program 组合本次运行资源；react 执行模型与工具循环    │
│ context / models / content / tools 提供各自能力            │
└────────────┬────────────────────┬────────────────────────┘
             ▼                    ▼
┌─────────────────────┐  ┌─────────────────────────────────┐
│ ledger：消息与事务   │  │ 模型 provider / shell / MCP 等   │
│ 记忆插件保存各自状态 │  │ 外部效果由相应 owner 负责         │
└─────────────────────┘  └─────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐

│ 管理装配、服务与事件、Fiber、任务作用域、资源回收           │
└──────────────────────────────────────────────────────────┘
```

这是职责示意，具体业务通过服务键和事件协作，并非所有请求按图中垂直顺序直接调用。

| 层次 | 入口 | 重点 |
|---|---|---|
| 启动入口 | [main.py](../main.py) | 命令分发、workspace、迁移、gateway 与 supervisor |
| 应用装配 | [bootstrap/app.py](../bootstrap/app.py) | `AppRuntime.start/run/shutdown`、锁、readiness、退出清理 |
| Core 装配 | [bootstrap/tools.py](../bootstrap/tools.py) | `build_core_runtime` 创建插件管理器，不创建业务数据库 |
| 插件加载 | [agent/plugins/manager.py](../agent/plugins/manager.py) | `PluginManager`、选中版本、live Root、局部更新 |
| 组合运行时 | [agent/plugin_composition/context.py](../agent/plugin_composition/context.py) | `Context`、`Fiber`、`CompositionRoot`、`RuntimeScope` |
| 插件业务 | [plugins](../plugins/) | 对话、模型、记忆、工具、唤醒均有独立 owner |
| 前端与协议 | [frontend](../frontend/)、[schema/app-server-v2.json](../schema/app-server-v2.json) | 展示、流式状态、控制协议，不作为消息事实来源 |

## 2. 先理解消息模型

从 [ledger/contract.py](../plugins/ledger/contract.py) 阅读 `Message`、`Input`、`Output`、`ToolCall`、`CallRef`、`ToolResult`、`Control`，再读 [turn_projection](../plugins/turn_projection/)。

| 概念 | 本项目中的作用 | 易错点 |
|---|---|---|
| Session | 归属消息、属性和作用域的会话 | 不等同于一次 HTTP 请求 |
| Message | 有身份与顺序的持久事实；包含来源和正文 | 不只是 `role/content` 字典 |
| Turn | 从消息与控制边界推导的交互过程 | 不固定等于“一问一答两条消息” |
| Input | 输入内容块，可带模型选择、附件引用等 | 来源不只限于网页用户 |
| Output | 内容块及工具调用，finish 为 continue/complete/quiet | 含 ToolCall 时必须为 continue |
| ToolCall | 固定 binding 与参数的工具调用 | 单独一个工具名称不足以确定历史调用 |
| CallRef | Output 的 message_id 加 part_index | 用于把结果关联回具体调用 |
| ToolResult | success/denied/error/interrupted 及内容 | “结果未知”是错误说明，不是当前独立 outcome 值 |
| Control | pause/resume/abandon/failure 控制事实 | 取消不能只理解为取消一个协程 |

普通流程示例：`Input → Output(ToolCall A、B) → ToolResult A → ToolResult B → Output(complete)`。Turn 的实际分段要回到投影实现核对。

## 3. 启动：源码存在不等于插件已运行

沿 `main.py:serve → build_app_runtime → AppRuntime.start → build_core_runtime → CoreRuntime.start → PluginManager.load_all` 阅读。

启动阶段会取得 workspace 锁，配置共享 HTTP 资源，装配并加载插件，启动适用的宿主监督任务，最后发布 readiness。失败时清理已经构造的资源；退出时先排空插件，再释放相应资源和锁。

业务数据库由插件初始化。例如 [ledger/plugin.py](../plugins/ledger/plugin.py) 的 `apply` 打开 `sessions.db`、`sessions-derived.db`、附件与入站相关存储，注册关闭责任，再发布窄接口；[models/plugin.py](../plugins/models/plugin.py) 管理模型注册库。

发行组合从 [bundles/base.toml](../bundles/base.toml)、[headless.toml](../bundles/headless.toml)、[minimal.toml](../bundles/minimal.toml) 看起。minimal 当前禁用全部行；用户 patch 可以再启用。Bundle 是组合输入，实际运行选择由 `plugin-stable.json` 保存。

注意：[ADR-0108](../docs/decisions/0108-bundles-are-composition-inputs.md) 标记为 proposed / implemented for review；可以讲当前实现，不能称为已完成最终验收。启动器构建发行制品也不代表运行时会直接采用你的 dirty 插件源码。

## 4. 对话与 ReAct 主链

### 4.1 输入、触发回复与程序装配

1. 从 [conversation/plugin.py](../plugins/conversation/plugin.py) 的 `apply` 内部 `accept` 看输入接纳：处理停止/恢复、会话属性、模型选择、附件引用，追加 Input。
2. 由 [sources](../plugins/sources/) 管理来源会话与控制，通过来源变化通知驱动消费者；conversation 不直接持有模型执行权。
3. [reply/plugin.py](../plugins/reply/plugin.py) 监听并调度待回复工作。继续跟踪 `SOURCE_CHANGED`、回复扫描与 `REPLY_PROGRAM`，而不是假设 `accept` 同步调用模型。
4. [reply_program/plugin.py](../plugins/reply_program/plugin.py) 发布 `REPLY_EXECUTE_V4`；[program.py](../plugins/reply_program/program.py) 的 `run_reply` 绑定模型、材料、内容检查、工具菜单、授权与 writer，最后调用 ReAct。

区分 `reply` 的自动触发职责与 `reply_program` 的本次程序装配职责。Wake 等来源也能使用回复执行能力。

### 4.2 ReAct 每轮做什么

主入口：[react/plugin.py](../plugins/react/plugin.py) 的 `react`。

```text
┌──────────────────────────┐
│ 读取已提交日志，结算旧调用 │◄────────────────────────┐
└────────────┬─────────────┘                         │
             ▼                                       │
┌──────────────────────────┐                         │
│ 固定快照，取得本轮材料     │                         │
└────────────┬─────────────┘                         │
             ▼                                       │
┌──────────────────────────┐                         │
│ Context 组请求，Model 生成 │                         │
└────────────┬─────────────┘                         │
             ▼                                       │
┌──────────────────────────┐                         │
│ 检查截断，解码内容与调用   │                         │
└────────────┬─────────────┘                         │
             ▼                                       │
┌──────────────────────────┐     continue             │
│ 事务核对前提，提交 Output │─────────────────────────┘
└────────────┬─────────────┘
             │ complete / quiet
             ▼
          结束本次程序
```

关键是先提交 Output，下一轮才结算其中的工具调用。模型返回的草稿不能直接触发外部操作。

按这些符号读，避免第一次从上到下硬啃整个文件：

| 符号 | 回答的问题 |
|---|---|
| `_History` | 如何从日志找到未结工具、执行边界和步数 |
| `_complete` | 请求如何组装、缩减，模型调用何时开始 |
| `react` 内的 `commit/narrow` | 新输入或控制变化到达后，旧草稿如何失效 |
| `_competing` | 哪些同来源的新事实会取代生成前提 |
| `_settle_pending` | 串行屏障与连续并行调用如何分组 |
| `_settle_group/_OrderGate` | 执行重叠时，如何保持结果提交顺序 |

正常装配传入 `state` 与 `check_start`，提交在 owner 事务中重新核对来源与日志竞争。源码还保留无 state 的 head 冲突处理分支，讲解时区分分支与正式装配路径。

### 4.3 工具执行与授权

继续阅读 [tools/program.py](../plugins/tools/program.py) 的 `ToolProgramFactory`、[menu.py](../plugins/tools/menu.py) 的 `ToolMenu`、[execution.py](../plugins/tools/execution.py) 的 `_settle_message/_invoke_message`。

执行至少经过 binding 解析、参数准备、权限核对、Task 生命周期和结果提交。给模型展示某项工具，不等于绕过执行时授权。`tool_search` 当前按插件 ID 加载获授工具 schema 并支持间接调用，不能凭名称声称用了向量语义检索。

并发模型：连续声明可并行的调用有界重叠执行；非并行调用形成屏障；`commit_after` 等待前驱提交。执行耗时不相加，批次延迟也不简单等于所有工具的最大耗时，因为还包含排队、屏障和写入。

## 5. 上下文、压缩、记忆分开学

| 能力 | 入口 | 要回答的问题 |
|---|---|---|
| 请求上下文 | [context/plugin.py](../plugins/context/plugin.py)、[materials.py](../plugins/context/materials.py) | `ContextBuilder` 如何用快照与已取得材料组装请求 |
| 摘要压缩 | [compaction/plugin.py](../plugins/compaction/plugin.py)、[message_summary.py](../plugins/compaction/message_summary.py) | 摘要覆盖哪个已结算区间，怎样引用原消息 |
| Markdown 记忆 | [markdown_memory/plugin.py](../plugins/markdown_memory/plugin.py) | profile 草稿、证据核验、投影与写入如何分离 |
| Akasha 学习与召回 | [akasha/application/consumer.py](../plugins/akasha/application/consumer.py)、[domain/readout.py](../plugins/akasha/domain/readout.py) | 消费进度与图怎样一致推进，召回如何产生 |
| 项目作用域 | [projects](../plugins/projects/)、[akasha/scopes.py](../plugins/akasha/scopes.py) | 不同 Project 的记忆图怎样路由 |

Context 的构造与材料获取分离：`build` 不负责临时联网检索或生成摘要。摘要范围由 `settled_prefixes` 等校验，避免切断工具请求与结果。缩小窗口改变模型看到的投影，不自动删消息。

Akasha 比“embedding 后 top-k”复杂。当前目录划分为 application/domain/infrastructure；domain 包含图、特征、Residual Push 扩散与多 basin readout。第一遍只理解输入、图、消费进度与召回输出；第二遍再推导算法。

恢复、补算向量、显式重建是三个动作：`MessageConsumer.load` 根据原绑定恢复材料；已有消费进度缺少学习图不会默默重学。重建走相同消费实现的重放，不能宣称任意删除图或向量库都必定可恢复。

## 6. 主动消息：判断、候选和送达各有状态

入口：[wake/plugin.py](../plugins/wake/plugin.py)、[wake/program.py](../plugins/wake/program.py)、[wake/request.py](../plugins/wake/request.py)、[eventmail](../plugins/eventmail/)、[drift/plugin.py](../plugins/drift/plugin.py)、[delivery](../plugins/delivery/)。

`wake/program.py:run` 按当前阶段选择固定工具并调用 `REPLY_EXECUTE`，对 screen/alert/investigate 等阶段设置不同步数与材料范围。由此可见主动执行也使用普通模型与工具程序能力。

Drift 当前插件发布持久 proposal 状态的窄服务；不要把它描述成无限自主思考线程。主动流程也不能简化为 cron 发一句话：候选、筛选、调查、提交与投递要分别跟踪。

输出写入账本和外部通道真正收到消息是不同事实。学习时沿 delivery 与 ledger 的 durable delivery 状态查看未知发送结果，而不是把 HTTP 成功等同于用户收到。

## 7. 组合运行时与热更新

先读 [context.py](../agent/plugin_composition/context.py) 的公开方法，再读实现细节：

| 概念/API | 学习要点 |
|---|---|
| `ServiceKey` | 用带类型的键表达服务合同 |
| `ctx.provide/require` | 注册与取得服务；要求和实际 owner 关联 |
| `ctx.inject` | 依赖满足时运行相应子结构，关注 provider 改变后的生命周期 |
| `ctx.effect` | 资源取得与清理责任绑定，观察逆序回收 |
| `Fiber` | 组合图中的生命周期节点；不是 OS 线程 |
| `RuntimeScope/OwnerCall` | 调用期间保留实际 owner 与资源使用范围 |
| `CompositionRoot` | 承载当前组合与拓扑；包括空组合 |

事件合同在 [events.py](../agent/plugin_composition/events.py)，明确区分 emit、serial、parallel、transform、observe 等形式。不要把“所有事件都异步并行”当成项目设定。

热更新要追踪提供者撤回、使用者排空、作用域失效、旧资源释放和新实现发布。只看 Python 模块 reload 无法解释数据库、工具 Task、端点和连接何时可以关闭。局部更新不等于把整个系统复制一份并任意切换。

## 8. 恢复与耐久性的四个边界

1. **同一次模型调用网络重试**：由 Models 管理；查看 [state.py](../plugins/models/state.py) 的 `_BoundChat.complete/_attempts`。临时错误可取消恢复，永久错误和预算耗尽需真实失败。
2. **ReAct 进程重启**：重新取得当前材料，生成新的请求身份，不恢复旧冻结请求。可能有重复生成费用。
3. **默认消息工具调用**：先复用已有结果；若调用早于当前进程且无结果，记录 error“结果未知”，避免自动重跑。见 `tools/execution.py:_settle_message` 与 [ADR-0100](../docs/decisions/0100-message-tool-calls-recover-at-turn-granularity.md)。独立程序调用的回执路径需另看。
4. **SQLite 提交与宿主断电**：MessageLog 和 ModelsStore 采用 WAL/NORMAL。项目接受普通进程崩溃恢复边界，不能把它扩大为断电后最近确认写入绝不丢失。见 [ADR-0099](../docs/decisions/0099-ledger-commits-use-wal-normal.md)。

取消等待、停止协程、终止外部进程、撤销外部副作用也是不同动作。面试中能举出“命令已执行但结果未落盘”的例子，比泛泛说有重试机制更有价值。
